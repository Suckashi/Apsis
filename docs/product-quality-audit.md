# Apsis 品質自我檢查

更新：2026-10-01。目標是持續提升到 Awwwards、Webby Awards、FWA 獲獎作品的品質；本文件記錄可驗證的進展與缺口，不把測試通過等同獲獎保證，也不給沒有依據的評審分數。

## 評估依據

[Webby 2026/2027 官方評審標準](https://www.webbyawards.com/judging-criteria/)包含內容、導覽、視覺、功能、互動、創新與整體體驗。Apsis 的自我檢查將這些面向落到清楚的任務入口、真實回饋、可使用的交付物、穩定操作與一致的品牌呈現。

[Awwwards Mobile Excellence 官方指引](https://www.awwwards.com/mobile-excellence-guidelines.pdf)是先前使用的手機專項指引，不能取代完整獎項標準。目前依使用者決定優先桌面。第七十一輪已經 Chrome 實際讀取 [Awwwards 完整評估頁](https://www.awwwards.com/about-evaluation/)及 [FWA 官方定位](https://thefwa.com/about/about-fwa/)，整理成 [整體品質驗收基準](award-quality-benchmark.md)。FWA About 未列出完整數值規則，仍不宣稱掌握或符合它們全部條件。

## 第四輪：長對話與載入成本

測例包含 80 輪對話，初次顯示最近 50 則訊息，每份執行紀錄附 36,864 bytes 工具輸出。原本開啟時讀取 25 份完整紀錄並查詢 25 個檔案狀態；輸入固定草稿又解析既有 Markdown 700 次。現在完成紀錄接近閱讀位置或被展開時才讀取，讀過的紀錄保留；執行中仍即時更新。未變動訊息沿用解析結果，語系切換仍會更新標籤。

| 同一測例的成本                  |          修改前 |           修改後 |
| ------------------------------- | --------------: | ---------------: |
| 初次完整紀錄請求                |              25 |                1 |
| 初次檔案狀態請求                |              25 |                1 |
| 初次紀錄回應大小                |   992,750 bytes |     39,710 bytes |

正式建置改用 React production 並壓縮程式碼；開發模式保留診斷。建置選項依 [esbuild 官方 API](https://esbuild.github.io/api/#minify)，兩種模式共用輸入與輸出設定。這是原始檔案大小比較，不是 gzip 後的下載量。

上述數字證明降低工作量與紀錄資料傳輸，不代表所有裝置的載入速度已達標。修改前單次 latest-ready 為 402 ms；修改後不同執行觀察為 323–1006 ms，包含並行測試影響，不能據此宣稱所有開啟操作更快。仍需實際弱網與低效能裝置的穩定測量。

回歸發現兩個真實邊界：橫向窄螢幕的「回到最新」浮動入口會遮擋工作詳情，已移到頂部；新話題尚未建立時可送出舊 context 指令，已增加 pending 狀態與送出／上傳保護，保留可編輯草稿。延遲 context 回應的測例確認 Enter 不會誤送，完成後可正常送出。

`npm run test:performance:browser` 檢查正式 JavaScript 700 KB 上限、初次完整紀錄／檔案狀態最多六次、草稿輸入不重解析，以及讀取延遲時仍能編輯、歷史分頁、再次閱讀復用、可見成果與無瀏覽器錯誤。檢查基於隔離資料。正式版聊天、工具回饋、Bot、手機與設定流程亦已驗證；實際使用者分頁已重載並操作歷史詳情、成果預覽及返回最新。

證據：`artifacts/conversation-performance/before.json`、`after.json`、`before.png`、`after.png`、`live-reading.jpg`；延遲新話題畫面位於 `artifacts/run-delivery/pending-topic.png`。

## 第五輪：輔助閱讀與鍵盤路徑

初次 axe 檢查發現未命名的附件輸入、聊天缺少一級標題、執行紀錄形成大量同名導覽地標，以及手機抽屜在 `aside` 上使用不適合的 dialog 角色。執行計時的普通 span 也有不支援的 aria-label，列在待人工檢查結果。這些結構已修正；每則訊息補上發話者名稱，Bot 名單按鈕改為名稱與必要狀態，避免把整段最新回覆當作按鈕名稱。

新增安靜的完成通知：只在目前 Bot 新增回覆時通知結果，可區分停止、中斷與失敗；不逐段讀出串流、不播報首次載入／歷史分頁／切換 Bot 的舊回覆、不移動輸入焦點。歷史失敗卡片與結果入口移除 live status，避免載入時重複通知。計時器明確關閉 live 更新。這個設計參考 [W3C 狀態訊息說明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)對非焦點通知與避免過量播報的要求；不代表已完成螢幕閱讀器語音實測。

`npm run test:accessibility:browser` 使用隔離資料與正式建置，涵蓋桌面空白、執行、核准、成果、預覽、中斷、設定，以及手機深淺色名單、預覽、對話，共 13 種狀態。目前自動判定違規為 0；另驗證串流期間不播報完成、回覆到達才通知、重新載入和 Bot 切換不重播、訊息與名單可讀名稱、Enter 開啟預覽、Escape 關閉及焦點返回入口。真正使用者分頁已重載，檢查新的訊息結構與成果預覽。

axe 仍列出裝飾符號的對比待判讀，以及手機 modal 背景 inert 時的 skip-link 待判讀；`incomplete` 保留在報告，不能當成已通過。既有 Bot 驗證的深淺色文字對比、200% 文字、抽屜焦點、縮減動畫均通過，但不取代完整人工評估。未執行 NVDA／VoiceOver 語音驗證，不宣稱 WCAG 全面符合或獲獎品質已達成。

本輪正式建置、accessibility、chat、tool-feedback、run-delivery、conversation-performance、mobile-composer、bots 瀏覽器驗證通過，隔離測例無 pageerror。加入通知後長對話測例仍只讀取一份初次完整紀錄、草稿輸入重解析 0 次，正式 JavaScript 583,465 bytes。

證據：`artifacts/accessibility/before.json`、`after.json`、`after-light.png`、`after-dark.png`、`live-reading.jpg`。修正前報告是 11 種狀態，修正後另補手機對話兩種狀態；不能將 11 與 13 當作相同總樣本直接評分。

## 第六輪：一致的成果預覽與版本定位

原本發布成果的卡片只能下載，修改檔案卡片則可預覽，形成兩種操作。現在發布成果與附件的卡片都以主區域開啟預覽、右側獨立下載；引用操作集中在預覽面板，避免每張卡片多一個散落的按鈕。右側面板的分類與關閉入口固定在頂部，捲動長成果時仍可操作。保持 Bot 身分、紫色系、聊天與按需開啟工作面板的方向。

成果預覽讀取發布快照，標示「發布時的版本」與時間；附件標示「上傳時的版本」。原工作檔案修改或移除，不會替換保存內容。缺少保存版本的舊紀錄只提供下載，不使用現有工作檔案冒充發布版本。工作檔案捷徑仍明示「目前內容」，兩者不混用。

支持 Markdown／原始碼、文字、單一 HTML、圖片、PDF，以及 DOCX／XLSX 文字預覽；Office 版面需下載，HTML 的獨立圖片／CSS／外部資源不包含在單一保存檔中。HTML 能執行自己的按鈕腳本，但維持 opaque sandbox 和 CSP，不可讀取主介面；不加入 allow-same-origin。未知格式與超過文字預覽大小的檔案提供清楚下載提示。預覽只在使用者開啟時讀取，切換選擇後忽略舊回應；錯誤可重試。

引用改為可讀成果名稱，請求仍使用正確的原始路徑與版本。只有保存引用成功才提示完成，等待時禁用重複操作。延遲引用期間切換 Bot 不會把結果加到另一位夥伴的草稿。模型執行上下文仍接收到實際 fileReferences，測例從引用路徑讀到正確保存內容。

`npm run test:artifacts:browser` 覆蓋八種格式／大小情境、來源移除／修改、Unicode 下載、Markdown 與原始碼、HTML 實際按鈕與隔離、圖片載入、PDF 入口與回應、Office 文字、未保存版本、重試、快速切換、舊話題與引用送出、引用失敗與 Bot 切換、附件預覽、草稿、375px 深淺色、44px 下載入口、Enter、Escape、展開後焦點返回、固定關閉入口與無 pageerror。四種新預覽狀態的 axe 自動判定違規為 0；裝飾符號對比與 inert 背景 skip-link 的 incomplete 仍保留待人工判讀。PDF 覆蓋入口與 HTTP 回應，不以它宣稱所有 PDF 的版面渲染正確。

真實模型以兩項操作交付既有番茄鐘，回覆「既有番茄鐘已交付，內容未修改。」。實際從成果卡片用 Enter 開啟，點擊開始、暫停、切換休息，顯示 05:00，並完成下載。下載 SHA-256 與當前原始 index.html 相同，也符合之前預覽 revision，瀏覽器 error logs 為空。本次沒有重新製作番茄鐘，亦沒有實際等滿 25／5 分鐘。

本輪 build、artifacts、accessibility、bots、work-files、run-delivery、chat、mobile-composer、tool-feedback、conversation-performance 均通過；保存成果、文件與跨話題交付的三項既有後端測試通過。正式 JavaScript 589,919 bytes，長對話測例仍是一份初次完整紀錄、草稿重解析 0 次。另修正效能測量程式關閉瀏覽器時未處理的 response.body promise；這是測試清理競態，非產品載入失敗。

最後補查互動狀態：測例把 HTML 計數增加到 1，展開預覽後讀到 0（`htmlStateAfterExpansion`），顯示 native Modal 重建 iframe，尚未保留互動狀態。主要流程的 PASS 不包含這項狀態保留要求。下一輪優先修正展開／收合時的 iframe 生命週期，並檢查工作檔案的相同情境。

證據：`artifacts/artifact-preview/report.json`、桌面／手機截圖、`live-preview.jpg`、`live-download.json`。完整獲獎品質仍未證明；本輪改進的是實際交付、預覽與引用流程的一致性，不取代後續互動狀態、整體品牌、弱網與長期使用評估。

## 第七輪：互動預覽生命週期

第六輪發現的展開重置已修正。成果與工作檔案現在保留同一個預覽 DOM 與 iframe，只切換尺寸、原生 modal 狀態與原始碼可見性。採用 [MDN dialog 的原生模式與顯示行為](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog)；面板內是具名稱的非 modal 預覽，展開後由 showModal 提供背景隔離。收合後等待 DOM 完成尺寸切換再還原焦點，避免落到主對話。

- 真實模型先前發布的番茄鐘：24:37 暫停 → 展開 24:37 → 原始碼／預覽 24:37 → Escape 收合 24:37；回到「展開預覽」焦點，瀏覽器 error logs 為空。沒有新模型生成或滿 25 分鐘計時測試。

- `verify-work-files`：使用含相對 CSS、圖片和 ES module 的網頁，原始碼切換、展開與 Escape 收合後計數仍為 1、可增加到 2；明確重新整理仍載入更新內容。

## 第八輪：弱網回饋、資料同步與恢復

補上正式程式載入前的輕量 Apsis 畫面，套用既有深淺色與快取語言；載入超過 10 秒提供重新載入入口。React 已啟動、資料仍在讀取時則顯示 Bot 名單佔位和準備說明。只有伺服器確認真的沒有資料才顯示空白歡迎，不把尚未載入說成沒有 Bot。首次與後續資料讀取失敗都提供 44px 重試按鈕，保留已載入內容、草稿與收合的錯誤詳情；恢復後可繼續輸入。

同步 GET 增加 15 秒讀取界線；它不停止後端任務，也不替送出訊息的 POST 設定這個逾時。伺服器已接受操作後，即使重新讀取失敗，也顯示資料同步問題，不把已送出的工作說成未送出。密集 SSE 事件合併成依序讀取與必要的下一次同步，避免慢回應一直被更新的請求作廢。瀏覽器離線時保留可編輯草稿與最後已知工作狀態，停用送出／上傳，重連後取回實際結果。

公開靜態程式與樣式使用 Brotli／gzip 協商及各表示版本的 ETag；瀏覽器必須重新確認版本，建置更新後取得新內容。私有 API 與帶 nonce 的 HTML 維持 no-store。協商依 [MDN Accept-Encoding](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Accept-Encoding)，壓縮使用 [Node zlib](https://nodejs.org/api/zlib.html)。單元測試驗證解壓內容、q=0、HEAD、304、不同壓縮表示與檔案更新，不靠載入畫面推定快取正確。

隔離 Chromium 測例：375×812、縮減動畫、150ms 延遲、下載 200,000 bytes/s、上傳 93,750 bytes/s、CPU 降速 4 倍、停用瀏覽器快取。這是 [Chrome DevTools Protocol 網路模擬](https://chromedevtools.github.io/devtools-protocol/tot/Network/)；CPU 係數不代表某款真實手機。

- 主程式 encodedBodySize 從 590,851 bytes 降到約 176,000 bytes；主樣式從 100,351 bytes 降到 17,079 bytes。這是下載的 body 大小，未含 HTTP header；解碼後的程式仍約 595 KB，並非移除同等程式碼。
- 修改前單次 host readyMs 15,196，修改後約 12.7 秒；這個時間含自動化與等待截圖，不能冒充 FCP／LCP。補記頁內 mounted／ready 及 Resource Timing；一輪主程式 responseEnd 約 2.8 秒、React mounted 約 11.5 秒。第九輪已確認此時間含本機外部腳本注入等待，不能全部歸因於產品程式；見下節隔離測量。
- 初次／後續讀取失敗、15 秒真實等待後的逾時與重試、草稿與焦點恢復通過。事件每 80ms 發送、讀取延遲 450ms 時，仍在任務執行中看到「同步進度 1」；背景同步依序進行，最多兩個 state 讀取來自背景與送出後的手動刷新。

桌面輸入框保留附件、模型及送出／停止；核准模式收斂為 44px 圖示入口，完整模式名稱保留在 accessible name 與滑鼠提示，展開後保留三種模式、目前選中狀態及生效範圍。移除桌面常駐快捷鍵說明，提示保留在 textarea 的 title。未修改使用者核准設定，也未改手機布局、模型回答或已有成果內容。

build／TypeScript 與 311 項整體測試通過；桌面聊天及設定瀏覽器回歸通過，設定驗證涵蓋三種模式的儲存、跨頁同步、衝突、失敗與焦點恢復。工具進度驗證同步檢查桌面資訊收合、失敗仍可見、核准不被收起、鍵盤開關模式選單與完整證據閱讀；驗證腳本的舊可見等待改為 attached，避免要求桌面已收斂的次級文字仍可見。正式 Chrome 核對空草稿、目前模式與新版輸入區，鍵盤展開／Escape 關閉正常，未提交模型任務。截圖保存在 artifacts/desktop-chat-refresh/live。

這一段改善桌面的執行資訊密度與輸入區，不宣稱完整品牌一致性、模型回答品質或所有長任務恢復已完成。

## 第一百零八輪：真實任務的中文輸出與驗證失敗

以正式模型執行合成的十二人讀書會企劃任務，Bot 產出 DOCX 與 PDF，並在使用者 Chrome 完成兩檔下載。PDF 三頁的繁體中文可讀，但預算表與總額跨頁；DOCX 確認有標題樣式、段落與表格，未經 Word 視覺排版驗證。靜態檢核頁的 `verify_web` 連續失敗，最後 run 標為 failed，沒有宣稱整項任務已完成。紀錄顯示驗證腳本點選被 label 覆蓋的 checkbox、等待隱藏的進度元素，以及將計算後的像素寬度當成百分比比較；這些是該次產物與驗證步驟的問題，不能據此歸咎 Apsis 的驗證器。

同一任務中的 Shell 輸出出現中文替代字元。根因之一是每個 stdout／stderr Buffer 區塊各自呼叫 `toString("utf8")`；另一個 Windows Python 管線輸出沒有固定 UTF-8。改為兩條管線各自持續解碼，並設定子程序的 `PYTHONIOENCODING=utf-8`。實際 Bash 回歸以跨區塊的中文字和 emoji 覆蓋兩條管線，Python 回歸檢查環境及中文輸出；原有指令結果與操作證據仍保留。這修復輸出可讀性，不代表該次 failed 任務自動恢復或所有外部程式都輸出 UTF-8。

`check:docs`、build／TypeScript、314 項完整測試、隔離 Shell 結果瀏覽器驗證，以及聊天瀏覽器回歸均通過。實際外部模型任務仍以 failed 結束，沒有把隔離驗證當作任務成功證據。

- 效能：長對話成本、隔離弱網／CPU 降速與啟動歸因已有證據；仍需真正低效能裝置、完整 LCP／INP、大型內容與更多頁面互動測量，不能只憑本機 fixture 判定達標。

- 無障礙：13 種狀態零自動違規，仍保留手機預覽摘要及長文裁切的原始 incomplete 與獨立對比／圖層檢查；已補安靜通知、發話者結構及手機抽屜閱讀動線，仍需完成螢幕閱讀器語音與完整產品流程的人工驗證。
- 穩定性：離線背景任務與重新連線已補隔離證據；仍需重現第一次 terminated，驗證外部模型長任務及跨話題恢復。
- 成果：原生 DOCX／PDF 已補 Markdown、來源直接轉換及修訂，已有外部模型採用、完整來源與同一次成果下載證據；DOCX 語意閱讀、一般表格及原文保留已補，並保留真實 Word 分頁與圖片未呈現的限制；多檔靜態網頁的不可變預覽、ZIP 及新話題引用已補隔離證據。已補真實模型多檔採用及使用者 Chrome 下載；仍需 Word 實際列印版面與複雜表格／大型文件。

- 桌面閱讀：第七十四輪已補延後紀錄載入時的開頭／結尾保持、中途閱讀與分頁回歸；更多真實大型內容及不同輸入裝置仍需持續驗證。
